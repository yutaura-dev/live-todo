# ADR-0025: 届いた事実は既存の Task の計画を育て、迷ったら提案にする

- **Status**: Accepted
- **Date**: 2026-11-28
- **Deciders**: YutaUra

## Context

これまでの振り分け（ADR-0019）では、届いた事実 1 件を「既存の Task の事実にする」「新しい Task を生む」「対象外」のどれかにし、迷ったら事実をユーザー待ちにしていた。生まれた Task は、さらに todo か要確認かに仕分けた。仕分けの画面には「振り分けを待っている事実」と「要確認の Task」の 2 種類が並び、違いが分かりにくかった。

要確認の Task は、「自分がやることか曖昧なまま Task にした」ために要るようになったもの。また、事実そのものを Task にする形だと、同じ件の事実が届くたびに Task が増えやすい。

作者の考えは次のとおり。

- 事実が届いたら、既存の Task に関係するものは緩めに自動で紐づける
- 新しい Task は、「この事実から、こういう Task をやるとよい」と AI が考えたもの。確信が高ければ自動で作り、迷えば提案する
- 新しい Task を作るより、既存の Task に紐づけて計画を育てる方向に力を働かせ、Task の数が必要以上に増えないようにしたい。ただし、期日などの事情で別の Task として扱ったほうがよい場合もある

## Decision

### 振り分け（specs/routing.spec.ts）

届いた事実について、AI は 3 つを別々に判定する。

1. **既存のどの Task の事実か**: 緩めに、いくつの Task にでも自動で紐づける。識別子（同じ URL・同じスレッド）で決まるものは同期が決める
2. **紐づけた Task ごとに、事実が求める作業を、その Task の計画に足すか**: 軸は「その Task の完了条件をすべて満たしたあとも、その作業をやる意味が残るか」（Decisions への問い）
   - 残らない（確率が低い）: 計画に足す
   - 中間: 寄せ先つきの提案にする（既定の操作は「足す」）
   - 残る（確率が高い）: 新しい Task の候補にする
3. **新しい Task を生むか**: どの Task の計画にも入らない作業ごとに（0 個のことも複数のこともある）、確信が高ければ自動で作り、中間なら提案、低ければ作らない

1 と 3 は両立する（既存の Task に紐づけつつ、新しい Task も生む）。AI が見たのに決められなかった（refusal・形に合わない）事実はユーザー待ちにする。AI に届かなかった（API が落ちている・時間切れ）事実は未振り分けのまま、次の同期でやり直す。

### 提案（specs/task-proposal.spec.ts）

提案は Task ではない（Task の数を増やさない）。関係する事実が届けば同じ提案に足し、確信が上がれば AI が自動で受け入れる。見送った提案は期限を置かずに、もとの事実が開いている間は残し、事実が行動を求めるように変わればもう一度提案する。もとの事実が片付けば取り下げる。

### Task（specs/task.spec.ts）

- 「仕分け中」「要確認」の列をなくす。Task は、やると決まったものだけ（自動で作った・提案を受け入れた・手で足した・定期の Task から作った・切り出した）で、できた時点で todo
- 「計画の項目を別の Task に切り出す」「別の Task にまとめる」を足す。まとめた Task は作業がまとめ先で続くので、完了の列には出さず、まとめ先の履歴から開けるようにする
- 終わった Task に関係する事実が届いたら、計画に足さず新しい Task にする

### 寄せすぎの歯止め

1. 完了条件が「未定」の Task には、自動で足さない（足す提案にする）
2. 識別子は判定 1 の材料にだけ使い、判定 3 の材料にはしない（同じスレッドに別の依頼が来ることはよくある）
3. 完了条件を満たしても、事実から計画に足した項目にまだのものが残っていれば、自動では閉じずに切り出しを提案する
4. 計画に足した項目の期日で優先度が上がったら、その項目を見通しのカードの行に出す（Prioritization に、段階を決めた Action Item を持つ）
5. 判定のたびに、問いの版と確率を記録する。切り出す・まとめる・外すは Task の出来事として残り、閾値を見直す材料にする

Task の優先度は、まだ済んでいない Action Item のいちばん早い期日も材料にして決める（期日の違いだけで Task を分けない）。

## Alternatives Considered

判断の軸は、7 つの役（Devil's Advocate・Future Self・End User・Steel-Manner・Pragmatist・Maintainer・AI 判定の設計者）で並列に検討し、Devil's Advocate と Steel-Manner で 2 回目の反論をした。

- **A. 一緒に終わるか（採用）**: Future Self・End User・Pragmatist・Maintainer・AI 判定の設計者が支持。Decisions の問い 1 つで書けて、後から再現できる。「一緒に終わるか」と未来を推測させる形だと確率が中間に割れるので、完了条件と比べさせる形に言い換えた
- **B. 同じ対象・同じ相手か**: 同じ相手の Task が雑多な依頼を吸い込み、閉じなくなる（End User・Future Self）。識別子の一致は判定 1 の材料として残した
- **C. 既存の Task の計画を変えるか**（Steel-Manner が推した）: 今の計画と比べるので局所的だが、紐づいた事実ならほぼ常に「はい」になり閾値で切れない（AI 判定の設計者）。計画の改訂案を Generation に書かせないと判定できず高い（Pragmatist）。「完了条件が未定の Task では A を判定できない」という指摘は、歯止め 1 として取り入れた
- **D. いつも寄せ、大きくなったら切り出しを提案する**: 判定は増えないが、誤りの後始末が毎朝の作業になる（Future Self）。判定のテストも書けない（Maintainer）
- **E. 迷えば新しい Task の提案に倒す**（Devil's Advocate が推した）: 寄せる力が弱くなる。中間を提案にするという考えは、寄せ先つきの提案として取り入れた

中間の確率の扱いは、「足して『迷って足した』と記録する」（Pragmatist・AI 判定の設計者）と「寄せ先つきの提案にする」（2 回目の Devil's Advocate・Steel-Manner）で割れた。間違いが見えるほうに倒す（fail closed）という決まりに合わせて、後者にした。

## Devil's Advocate からの反論（残るリスク）

- 寄せすぎて間違えると、カードが減る方向に効くので、気づく手がかりが少ない。切り出す・まとめる・外すの回数を記録して閾値を見直す仕組みがなければ、軸が働いているかを確かめられない
- 事実から足した項目を完了条件にするかどうかで、Task が閉じない・項目が道連れで消える、のどちらかが起きうる（歯止め 3 で、自動で閉じる前に止める）

## Consequences

### Positive

- Task の数が増えにくく、同じ件の作業が 1 つの Task の計画に集まる
- 仕分けの画面は「AI の提案を受け入れるか決める場所」になり、置き場が 1 種類になる
- 要確認の列がなくなり、Task はどれも「やると決まったもの」になる

### Negative

- 判定 2 は紐づけた Task の数だけ Decisions を呼ぶので、費用が増える。自動で紐づける数に上限は置かず、判定 1 の精度で抑える
- 提案が溜まると、朝の後始末になる。中間の幅は狭く始め、受け入れた割合を見て閾値を動かす

### 見直す条件

- 切り出すが毎週何度も使われるなら、寄せすぎ。閾値を新しい Task の側に動かす
- 提案が毎朝いくつも溜まるなら、中間の幅を狭める
- 実データで判定 2 の確率が 0.5 付近に集まるなら、問いの言い方か、軸そのもの（C など）を見直す
