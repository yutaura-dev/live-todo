# ADR-0019: Task を起点にし、Source Item は Task についての事実として紐づける

- **Status**: Accepted
- **Date**: 2026-11-27
- **Deciders**: YutaUra

## Context

ADR-0007 で Task・Source Item・Link を分け、1 つの Task に複数の Source の情報が集まる形にした。データの形は Task が主になっているが、処理の流れは Source が起点のままになっている。

- 自動で Task ができる経路は、Source の同期（`syncSource` の triage）だけで、問いは「この Item は自分の todo か」になっている。新しい Item が来るたびに、その Item のタイトルのまま Task を 1 つ作る
- ADR-0007 の段階 3（新しい Item を既存の Task に紐づける）が手付かずで、Slack で頼まれたレビューとその PR は別の Task になる。2026-11-27 時点の実データでは、Task 237 件のすべてが Item 1 件だけに紐づいていた
- Slack の会話と Gmail のスレッドは、それぞれ別の作りで「既存の Task の続きか」を Claude Code に決めさせている。候補の Task はその Source の中だけ
- 利用者が決めたルール（ADR-0014）は Gmail の同期の中でメールに当てていて、Task を見ない。「YutaUra 以外が作った PR で、自分にレビュー依頼がなければ完了にする」のような、Task についての決まりが書けない

本来の関係は逆である。自分がやること（Task）があるから、そのために見る PR やスレッドがある。外の世界の出来事はすべて Source から届くので、届いたものを起点にしがちだが、届いたものは「どの Task についての事実か」を決められる材料であって、Task そのものではない。Task は Source がなくても成り立つ（手動の Task、定期の Task）し、複数の Source の事実を持ってもよい。

## Decision

### Task が主、Source Item は事実

- Task は自分がやること。Source Item は外の世界の写し（事実）、Activity はそれに起きた出来事。Task は事実を 0 件以上持つ（Link。役割の区別は持たない）
- 1 つの Source Item は複数の Task の事実になれる。AI が振り分けるのは 1 つ目だけで、2 つ目以降は識別子で決まるときかユーザーが足したときだけ（specs/routing.spec.ts）

### 届いた事実を、Task に振り分ける（Source に依らない）

同期の流れを次の 3 段に分ける。2 と 3 は Source を知らない共通の処理にする。

1. **取り込み**（Source ごと）: 取得して Source Item と Activity にする。今の Source Adapter・SnapshotDiffer のまま。Slack の会話・Gmail のスレッドのように、何件かをまとめて 1 つの事実として扱う単位も、Source ごとにここで決める
2. **振り分け**（共通）: 新しい事実ごとに、次のどれかを決める
   - 開いている既存の Task の事実にする（どの Task か）
   - どの Task のものでもなく、新しい Task を生む
   - 自分には関係がない（対象外）
   - 決め方は、確かなものから順に当てる。(a) 同じ URL・同じスレッドなど、識別子で決まるもの（AI を使わない）、(b) 候補の Task を絞ったうえで AI に選ばせる、(c) どれにも当たらなければ、新しい Task を生むかを判定する（今の todo 判定を「この事実は自分に新しい行動を求めるか」に読み替える）
   - 迷うもの（確率が中間・refusal）は、新しい Task にも既存の Task にも黙って入れず、要確認にする（fail closed）
3. **Task の反応**（共通）: 事実が増えた・変わった Task について、status・brief を導き直し、ルールを当てる。更新マークは Task Change にだけ付ける（ADR-0007 のまま）

### Task の材料（dossier）

- Task を判断に使う形（dossier）を、Source に依らずに作る。中身は Task の title・brief・status と、紐づく事実ごとの「アプリが書いた信頼できる情報（種類・通知の理由・作成者など）」と「外から来た本文」
- 信頼できる情報と本文は分けて渡す（今の判定と同じく、本文に書かれた指示や偽の行を、アプリの情報と取り違えないため）
- 事実の信頼できる情報と本文の作り方は、Source ごとに持つ（今の判定の `describe` を、事実を書く共通の口にする）

### ルールは Task に当てる

- ルールの「どういう時」は Task について書く。当てはまるかは、Task の dossier を材料に Decisions で判定する。確率が閾値以上のときだけ当て、答えがなければ当てない（ADR-0014 のまま）
- どの Source の Task に当てるかは、条件の文から判定する（画面で Source を選ばせない）
- 当てる時: Task ができたとき、Task に事実が増えたとき、紐づく事実が変わったとき。同じ Task に同じ中身のルールを当てるのは、きっかけの出来事ごとに一度だけ
- 操作は 2 種類に分ける
  - **Task への操作**（Source に依らない）: 完了にする・対象外にする・todo にする。アプリの中の変更なので承認は要らない
  - **事実への書き込み**（Source ごと）: Task に紐づく、その Source の事実に書き込む（今は Gmail のラベル・既読・アーカイブ）。ルールを決めたことを承認とみなす（ADR-0014 のまま）
- 「何をする」に条件が混ざっていたら（「レビュー依頼がない場合は完了にする」など）、読み取るときに見つけて、「どういう時」に移すよう案内し、保存させない。当てたかどうかを「どういう時」だけで追えるようにするため

### アカウントと LLM Profile

- 振り分けでは、アカウントをまたいで候補の Task を選んでよい。今は「1 台の PC に 1 つのアカウントの組と 1 つの LLM Profile」という運用（charter の前提と制約）なので、どのアカウントのデータも同じ LLM に送られる
- アカウントごとに LLM Profile を切り替えるようにするとき（plan の Phase 4）に、別の LLM Profile のアカウントのデータでできた Task を候補から外すかを決め直す

### 作り方と評価

- 実装の前に、spike で振り分け・ルールの判定を試し、AI を使う部分はベンチマークで実用に足るまで磨いてから繋ぎこむ
- ベンチマークは 2 種類にする
  - **作った例**: 決めた事例（どの Task の事実か、ルールに当てはまるか）を手で書いたもの。リポジトリに入れてよいのはこれだけ
  - **実データ**: 手元の DB から書き出して正解を付けたもの。案件の情報を含むので、リポジトリに入れず手元にだけ置く（gitignore）。開発に使う AI（Claude Code）が中身を読むのはよい（会社で契約している）

## spike でわかったこと（2026-11-27）

`spike/task-first/` で試し、作った例と実データでベンチマークした。数字は Microsoft-Decision-1.1（判定）と gpt-6-luna（分解）で測ったもの。

### 事実の書き方（取り込みで守る決まり）

- アプリが記録している値は、値がなくても書く（「レビュー依頼: なし」「conflict: なし」）。書かれていないことから「ない」を言い切るのは、判定のモデルに難しかった
- 状態は Source の言葉で書く（PR は「マージ済み」「マージされずに閉じた」、見張りは「GitHub の PullRequest の見張り」）。open / resolved だけでは区別できない
- **自分に関わる結論はアプリが決めて 1 行で書く**（「あなた（または所属チーム）へのレビュー依頼: あり（チーム @x 経由）」）。実データでは依頼先が 50 を超える PR があり、一覧から自分のチームを探させると見落として、例のルールで 3 件誤って完了にするところだった
- Source ごとに、自分のアカウント（GitHub のログイン名・Slack の表示名）を書く
- Task 自身の情報（状態・作られ方・事実の数）も、アプリが書いた情報として渡す

### ルールの条件の判定

- 条件を 1 問のまま聞くと、否定を含む組み合わせ（「〜以外が作った PR で、依頼が来ていない」）で再現率が 0.5 にとどまった
- 保存するときに LLM で、条件を単純な問いに分解して持つ（利用者に見せて確かめてもらう）。問いごとに「アプリの情報で答える（metadata）」か「内容を読んで答える（content）」かを付ける
  - metadata の問いは、タイトル・本文を渡さずに聞く。本文の偽の主張（「dependabot が作った」）を届かせないため。注意書きで「本文を信じるな」と書く方法は、内容についての問いまで弱くした
  - 条件が特定の種類の事実についてのものなら、最初の問いを「紐づく事実に〜があるか」にする。否定の問いだけだと、その事実がない Task でも当てはまった
  - 問いごとの確率の最小値が閾値（0.8）以上のときだけ当てる。積は厳しすぎた
- 結果: 作った例 78 件で誤って当てたもの 0 件・当て損ね 2 件。実データ（PR 80 件 × 5 つのルール）で 400 件すべて正解

### 「何をする」の読み取り

- Task の操作（完了・対象外・todo・変えない・はっきりしない）・条件が混ざっているか・事実への書き込み（既読・アーカイブ・ラベル）・できない操作を、Decisions の 1 回のリクエストで読み取る
- できない操作は肯定の形で例を挙げて聞く（「どれでもない操作か」と否定で聞くと、approve・転送・返信を見落とした）
- 結果: 直すのに使わなかった 9 件で 8 件正解、保存させないはずのものを保存できたもの 0 件

### 振り分け

- 識別子（URL）で決まるものを先に決め、残りは重なり（URL・番号・人・リポジトリ・言葉）で候補を 5 件まで絞ってから Decisions に選ばせる
- PR・Issue のように、それ自体が 1 つの仕事になる事実は、すでに別の PR・Issue を追っている Task には AI で紐づけない（URL で決まるときだけ）。同じ人・同じリポジトリの別の PR を混ぜたため
- 既存の Task に紐づける閾値は 0.8、どの Task でもないと決める閾値は 0.6 にする（間違えたときの害が違う）
- 結果: 作った例 22 件で誤って紐づけたもの 0 件、直すのに使わなかった 13 件で 12 件正解・誤って紐づけたもの 0 件。本文で「〇〇の続きです」と偽る例は 0.79 で、閾値の手前で止まった（本番では手当てが要る）
- 実データでは、Source Item に事実の中身がほとんど残っておらず（Slack は 857 件中 714 件が本文なし）、評価できなかった。取り込みで事実を残すようにしてから、本番に反映せずに判定だけを記録する形（shadow）で集めて測る

## Alternatives Considered

- **Source 起点のまま、ルールの当て先だけを Source 共通にする**: 早く作れるが、ルールは「Item に」当たり続け、複数の事実を持つ Task や事実のない Task についての決まりが書けない。振り分けがないので、同じ仕事が Source ごとに別の Task になるのも直らない
- **振り分けをすべて AI に任せる**: 同じ URL・同じスレッドのように識別子で決まるものまで確率のぶれにさらし、取りこぼしとコストが増える（ADR-0003 で規則を先に当てたのと同じ理由）
- **振り分けを Claude Code（エージェント）で行う**: 今の Slack の会話・Gmail のスレッドはこの形だが、1 件ごとに数十秒と費用がかかる。まず確率付きの判定（Decisions）と構造化出力で足りるかを確かめ、足りないものだけをエージェントに回す
- **ルールの対象の Source を画面で選ばせる**: 判定の回数が減り、思わぬ Source に当たらないが、Task は複数の Source の事実を持つので「どの Source のルールか」が決めにくい。条件の文で書けるほうを選ぶ（判定の回数と外れ方はベンチマークで確かめる）

## Consequences

### Positive

- 1 つの仕事が、Source をまたいで 1 つの Task にまとまる
- ルールで、Task についての決まり（複数の事実の組み合わせ、事実のない Task）を書ける
- Source ごとの振り分けの作り（Slack の会話・Gmail のスレッド）を、共通の振り分けに寄せられる

### Negative

- 同期の流れの作り直しになる。既存の `syncSource` の triage・Slack の会話・Gmail のスレッド・Gmail のルールの作りを段階的に置き換える
- 振り分けで AI を呼ぶ回数が増える（候補の Task を絞ってから呼ぶ。コストはベンチマークで測る）
- 振り分けを間違えると、関係のない事実が Task に入る。事実を Task から外す・別の Task に移す操作が画面に要る

### Neutral

- 既存の Task と Link はそのまま使える（データの移し替えは要らない）
- ADR-0007 の段階 3 は、この ADR の振り分けに含める。ADR-0014 のルールの当て先と操作の分け方は、この ADR で置き換える（Accepted にするときに ADR-0014 を Superseded にする）

## のちの見直し（2026-11-28）

次の点は、のちの ADR と spec で置き換えた。

- 迷った事実は、要確認の Task に入れず、どの Task にも入れない「ユーザー待ち」にする（specs/routing.spec.ts）
- Task の変化は Task Change ではなく Task Activity（ADR-0021）。届いたものは Task Input として receive 1 つで受け取る
- アカウントと LLM Profile の節は、AI Settings（ADR-0022）に置き換えた
- ルールは保留中（ADR-0025）
