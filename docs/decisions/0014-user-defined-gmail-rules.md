# ADR-0014: 利用者が決めたルールは、決めたことを承認とみなして自動で当てる

- **Status**: Accepted
- **Date**: 2026-11-26
- **Deciders**: YutaUra

## Context

請求書のメールが届いたら「レシート」のラベルを付けて既読にする、のような決まった片付けを、毎回承認して行うのは手間がかかる。
一方で charter は、外部への書き込みは必ずユーザーの承認を経て、全自動では行わないと決めている。

ルールの中身（どんなものに何をするか）は人によって違うので、アプリに組み込むべきではない。また、ルールは Gmail だけのものではなく、
「請求書に関するメールが来たら〜」のように、条件の中で何に当てるかを言葉で書けるほうが分かりやすい。

## Decision

- ルールは Source とは別に、設定の `rules` に持つ。利用者が設定画面で決める
  - 条件は言葉で書く（「請求書や領収書に関するメール」など）。当てはまるかは Decisions で判定し、確率が 0.8 以上のときだけ当てる。答えが返らなければ当てない（自動で書き込むので、迷うものには当てない）
  - 操作は Source ごとに持つ。今は Gmail のラベルを付ける（なければ作る）・既読にする・アーカイブするだけ。ゴミ箱に入れる・送るなど、ほかの操作は書けない（設定の検証で断る）。Slack・GitHub の操作は、要るものが決まったら足す
- 利用者がルールを決めたことを、そのルールの範囲の書き込みの承認とみなし、当てはまるものに自動で当てる。charter の「承認なしでの外部への書き込み」に、この例外を書き足す
- 判定するのは、ルールを作ったあとに届いたものだけ。過去のものにまとめて書き込まない
- 同じものを同じルールで判定するのは一度だけで、当てはまったか・何をしたか・確率を `gmail_rule_runs` に残す。失敗してもやり直さない（書き込みを二重に効かせないため）
- 判定に渡すのは件名・差出人のアドレスと表示名・種類・用件。条件は Decisions の指示の側に入れ、メールの中身と取り違えないようにする
- アプリが自分で決めたルール（組み込みのルール）で書き込むことはしない

## Alternatives Considered

- **毎回、案内を出して承認してもらう（日程が過ぎた招待と同じ）**: charter のままでよいが、決まった片付けのたびに手が要り、ルールにする意味が薄い
- **条件を項目（用件・差出人・件名）で選ばせる**: 判定は安く確実だが、「請求書に関するメール」のような書き方ができず、選べる項目に縛られる
- **アプリに「請求書はレシートに」のようなルールを組み込む**: 人によってラベルや片付け方が違うので合わない

## Consequences

### Positive

- 決まった片付けを、毎回承認せずに済む
- 条件を言葉で書けるので、項目に縛られない
- 何をしたかが残るので、ルールが思わぬものに当たっても後から追える

### Negative

- 判定は確率なので、外れることがある（操作をラベルの付け外しに限り、ゴミ箱や送信はできないようにしている。Gmail で元に戻せる）
- 届いたものごとに、ルールの数だけ Decisions を呼ぶ（1 回 $0.00005 程度）
